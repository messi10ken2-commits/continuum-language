## データごとの削除と保持

| 区分 | 現在の処理 | 追加運用 |
| --- | --- | --- |
| アカウント、パスワード、ログイン・回復token | 元のusers行と関連行を削除 | 旧端末の認証が無効であることを確認 |
| プロフィール、学習履歴、課題・提出・個人メモ・保存音声 | manifestに沿って削除 | 未知のusers外部キーがある場合は処理停止 |
| 私的チャット・サポート本文 | 対象会話の本文・関連データを削除 | 相手に残る最低限の予約状態との違いを説明 |
| APNs登録・配送キュー | セッション／ユーザー削除に連動 | OSの表示済み通知や相手の保存済みコピーの遠隔消去は保証しない |
| 将来予約・利用券 | 将来予約を取消、未使用券の権限を失効 | 先にキャンセル・返金・講師対応を処理。コードは返金や外部購読解約をしない |
| 保持対象の構造 | 非ログインのDeleted accountに付け替え、自由記述等を除去 | provider customer/transaction ID等は個人と再結合しうる。完全匿名とは呼ばない |
| 暗号化メールpayload | 送信または期限終了で消去 | 送信記録と本文の保存は別。未送信を「到着」としない |
| 削除証跡 | receipt、担当者、件数、policy version、見直し予定日 | 期限到来時の自動保持記録消去は未実装。台帳で手動対応 |
| 外部AI、決済、メール、ログ、端末保存 | DB削除だけでは一括処理しない | 実際の利用provider、保持・削除手順・依頼結果を確認する |

## 管理者の実行手順

1. Account内の本人パスワード付き申請を確認し、本人に処理範囲・目標期間・購読解約の別手続きを案内する。
2. 今後の授業、残券、購読、請求、返金、通報・紛争の有無を確認。支払い先側の対応を実施する。
3. バックアップのinventoryと外部providerの扱いを確認し、公開済みpolicyのversion・期間が実設定に一致することを確認する。
4. Administration → Account deletionでpreview。名前・対象・件数・未知schemaを確認。変更があれば再preview。
5. 受付IDと元user UUIDだけを含む復旧時の再削除台帳を、復旧対象DBと独立した暗号化・アクセス制限付き保管先に保存する。メール・本文は不要。保管先と期限の承認が必要で、現時点で外部台帳は自動作成されない。
6. 外部データ、バックアップ、保持、共有履歴、通知先、本人への説明の各チェックを完了し、DELETEと管理者パスワードで実行する。
7. アカウント・セッション・個人データが消え、無関係な利用者が維持されていることを確認。receiptを台帳に追記する。
8. 完了メールの配送状態を確認。失敗は再試行・期限・担当者対応を追跡。provider受付は受信証明ではない。
9. 30日ごとに保持記録・外部対応・バックアップ期限を見直し、不要な台帳も期限後に消去する。

本番のACCOUNT_DELETION_ENABLEDとACCOUNT_DELETION_POLICY_PUBLISHEDは、名義・期間・外部処理・実バックアップ証拠・メールが揃ってから有効化する。数値を仮入力して準備済みに見せない。

## バックアップ確認票

保管先ごとに次を記録する。秘密のDB接続情報やdump本体をGitHub・チャットに載せない。

- volume/service/environment、schedule ID、頻度、retentionSeconds、最新成功時刻、失敗監視。
- 手動snapshot・PITR・旧unmounted volume・外部dumpの有無と各expiry。
- 担当者とアクセス範囲、暗号化、削除期限、保持例外、復旧テスト日。
- 目標RPO 24時間・目標RTO 24時間を第一案とする。復旧実測前にSLAとして公開しない。

Railwayの公式説明には日次6日・週次約1か月・月次約3か月のscheduleがあるが、これは当プロジェクトの有効設定の証明ではない。実APIのretentionSecondsとbackup expiryを優先する。

## 復旧時の再削除

バックアップを戻すと、削除したuserと古いセッションも復活する。復旧DBはネットワーク隔離し、アプリとメール・APNs・課金workerを停止したまま検証する。

1. 元本番には上書きせず、承認済みの隔離DB／volumeに復旧する。
2. 復旧時点以後の、独立した暗号化削除台帳を照合。承認済み保持例外も再確認する。
3. 対象申請の新previewを作り、再削除する。復旧前fingerprintは再利用しない。バックアップが申請受付より古く申請行を含まない場合は、独立台帳の元user UUID・受付証跡と照合して管理者が申請を再構成する必要がある。現状、このインポート経路は自動化・検証されていないため、そのケースでは復旧公開を停止し、担当者による追加対応を行う。今回の自動テストは申請行を含むバックアップの再削除を検証する。
4. 対象user、セッション、個人データの消去を確認。無関係な利用者と必要な最小取引記録を確認。
5. 復旧で戻ったメール・プッシュのキューを照合し、古い予約通知や削除完了通知の重複送信を防ぐ。処理中はworkerを再開しない。
6. 最新の外部課金状態等も再照合してからアプリを公開し、必要なworkerだけを順に再開する。
7. 復旧元／旧volumeを含むコピーの期限管理を続ける。復旧によって削除期限が無期限に延びないようにする。

account-erasure.test.mjsは本物のPGlite data directoryをexport→別DBへload→削除再適用し、元user/セッション消去と他利用者維持、暗号化通知のローカル配送を確認する。Railway snapshot復旧、外部provider消去、Gmail実受信の証拠ではない。
